1. Executive Technical Summary & Architectural Philosophy

1.1 Project Operational Scope & Mandate

The National Digital Library of India (NDLI) Club Management and Employee Activity Tracking System is an enterprise web platform commissioned to manage, track, and audit institutional clubs nationwide across all 36 States and Union Territories. Coordinated under the Ministry of Education, Government of India, and governed by the Central Administration Office at the Indian Institute of Technology Kharagpur (IIT Kharagpur), the system bridges 7 Regional Zonal Officers with central executive leadership.

1.2 Core Architectural Principles & Design Decisions

⚙️ Zero External Dependency Kernel

Engineered entirely using Python standard library primitives (http.server, csv, hashlib, hmac, secrets, threading, json). Requires no third-party package runtime (e.g., Django, Flask, or SQLAlchemy), eliminating dependency hell and container CVE surface.

🔒 Multi-Tiered Cryptographic Protection

Passwords encrypted using PBKDF2-HMAC-SHA256 with 100,000 rounds and 16-byte random salts. Sensitive actions (such as Emergency Restore) require a Dual-Layer Security Challenge (dynamic Canvas CAPTCHA + Master Admin password re-authentication).

🗄️ Flat-File Atomic CSV Database Engine

Bypasses complex database servers (PostgreSQL/MySQL) by implementing thread-safe atomic file mutex locks with temporary file write-and-replace semantics (os.replace) guaranteeing ACID-like consistency on plain-text CSV stores.

🌐 Hybrid Cloud / Serverless Webhook Mirroring

Combines a primary Python container service (Render/Docker) with an automated Google Drive / Google Apps Script (GAS) Webhook Relay pipeline, executing real-time cloud data mirroring and 7-day rolling ZIP archives.

1.3 Purpose of this Technical Manual

This manual is compiled for technical handover, source code audits, and operational transparency. It provides full disclosure of underlying algorithms, cryptographic implementations, directory hierarchies, schema definitions, REST API contracts, and disaster recovery procedures.

3. Cryptographic Security & Authentication Subsystem

3.1 Password Encryption: PBKDF2-HMAC-SHA256

User credentials stored in data/master/master_users.csv and regional credentials.csv are never stored in cleartext. The system employs Password-Based Key Derivation Function 2 (PBKDF2) using HMAC-SHA256:

DerivedKey = PBKDF2(PRF = HMAC-SHA256, Password, Salt = 16_bytes_random, Iterations = 100,000, dkLen = 32_bytes) 
# Implementation excerpt from auth.py
def hash_password(password: str, salt: bytes = None) -> tuple[str, str]:
    if salt is None:
        salt = secrets.token_bytes(16)
    key = hashlib.pbkdf2_hmac(
        'sha256',
        password.encode('utf-8'),
        salt,
        100000,
        dklen=32
    )
    return key.hex(), salt.hex()

def verify_password(stored_hash_hex: str, stored_salt_hex: str, password_attempt: str) -> bool:
    salt = bytes.fromhex(stored_salt_hex)
    attempt_key = hashlib.pbkdf2_hmac('sha256', password_attempt.encode('utf-8'), salt, 100000, dklen=32)
    return hmac.compare_digest(stored_hash_hex, attempt_key.hex()) # Constant-time comparison

3.2 Session Entropy & Token Management

  • Token Generation: Tokens are 24 cryptographically random bytes generated via secrets.token_hex(24) (yielding 48 hexadecimal characters, 192 bits of entropy).
  • Timing Attack Resistance: Hash comparisons use hmac.compare_digest() to ensure constant-time execution, mitigating side-channel timing analysis.
  • Session Segregation: Client sessions are compartmentalized into distinct keys in sessionStorage: ndli_token (generic auth), ndli_admin_token (master control), and ndli_employee_session (zonal node context).

4. Dual-Layer Security Challenge for Disaster Recovery

4.1 Threat Model & Operational Rationale

An emergency database restore is an inherently destructive, non-reversible operation that overwrites both Central Master CSVs and all 7 Regional Node CSVs with historical snapshot data. To protect against accidental clicks, cross-site request forgery (CSRF), and unauthorized workstation access during active admin sessions, the system implements a Dual-Layer Security Challenge:

6. Flat-File ACID Simulation & Mutex Concurrency Engine

6.1 Concurrency Architecture: Thread-Safe Mutex Locking

In high-concurrency environments with multiple regional officers logging data simultaneously, standard file writes risk race conditions and torn writes. The system implements a dedicated Atomic CSV Engine (db/csv_engine.py) guaranteeing ACID properties on flat files:

CONCURRENT WRITE REQUEST (Worker Thread) | v [Acquire threading.Lock() for specific file path] | v [Read existing CSV content into in-memory dictionary cache] | v [Apply row insertions / upsert modifications] | v [Write new content to temporary scratch file: filename.csv.tmp.PID] | v [Flush to disk buffer via os.fsync(fd)] | v [Execute atomic filesystem rename: os.replace(tmp_file, target_file)] | v [Release threading.Lock()] ---> WRITE TRANSACTION COMMITTED SAFELY

6.2 ACID Property Implementation Matrix

ACID Property Standard RDBMS Mechanism NDLI Flat-File CSV Engine Implementation
Atomicity Write-Ahead Log (WAL) & Rollback Files are written to a temporary sibling file and committed via os.replace(). An atomic POSIX/NTFS syscall guarantees all-or-nothing writes.
Consistency Schema constraints & foreign keys Strict validation in Python layer: verified email formats, enum matching, and mandatory Rule 10 renewal date invariants.
Isolation Transaction isolation levels Granular file-level threading.Lock() prevents concurrent dirty reads or interleaved write streams.
Durability Disk flush and battery cache Synchronous flush() ensures data is written to underlying disk blocks before returning HTTP 200.

8. Synchronization & Node-to-Master Reconciliation

8.1 Incremental Sync vs. Full Batch Reconciliation

The system utilizes a dual-mode synchronization model:

  • Real-Time Incremental Sync: Triggered whenever a zonal officer submits an activity in SEC A or authorizes a club in SEC B/C. Writes directly to the local node CSV, then immediately invokes an atomic append to the master CSV file.
  • Full Node-to-Master Reconciliation: An authoritative audit tool operated via POST /api/sync/reconcile (or the admin dashboard button). Designed for recovery after backup restoration or network partition.

8.2 Full Reconciliation Algorithm (sync_engine.py)

Step 1: Iterate over all provisioned employee directories (data/employees/emp01..07) Step 2: Read employee clubs.csv and activity_log.csv Step 3: Build in-memory lookup index of existing master_clubs.csv by Club ID Step 4: For each node club: - If Club ID not in master index: Append to master_clubs.csv (Zero Overwrite Loss) - Validate ISO-8601 timestamps & verify renewal date invariant (+1 year) Step 5: For each node activity: - If activity not in master_activities.csv: Append with atomic lock Step 6: Recalculate Quotas: - Count verified clubs per officer - Count verified support logs per officer - Overwrite master_quotas.csv with true reconstructed tallies Step 7: Return summary payload: { "reconciled_clubs": N, "reconciled_activities": M }

8.3 Quota Recalibration Guarantees

Because quotas are recalculated directly from raw historical transaction rows rather than incremented counters, any manual CSV edits or historical data imports are immediately harmonized without quota drift or double-counting.

13.1 7-Day Autonomous Rolling Backup Daemon (backup_engine.py)

The platform features an autonomous background backup daemon running on a 7-day schedule. When triggered, it archives all critical database files into a timestamped, compressed ZIP snapshot:

├── master/
│   ├── master_clubs.csv

    ├── emp02/ ...
    └── emp07/ ...

13.2 Strict 2-Version Rolling Retention Invariant

To prevent unbounded disk consumption on cloud containers, the engine enforces a strict retention invariant: only the 2 most recent snapshots are preserved. All older snapshots are automatically unlinked: 

def prune_old_backups(backup_dir: Path, max_retained: int = 2):
    backups = sorted(backup_dir.glob("backup_*.zip"), key=os.path.getmtime, reverse=True)
    for old_backup in backups[max_retained:]:
        try:
            old_backup.unlink()
            logger.info(f"Pruned historical snapshot: {old_backup.name}")
        except OSError as e:
            logger.error(f"Failed to prune snapshot: {e}")

13.3 Google Drive Webhook Relay Pipeline

Every generated backup is mirrored offsite to Google Drive via an HTTPS Webhook relay connecting to Google Apps Script. This provides redundancy against container failure or cloud host termination.

Observed Symptom Root Cause Diagnostic Remediation Procedure
